## Databases & connection strings (where your Azure details go)

The app supports **two database providers**, switched by configuration — no code changes:

| Setting | Value | When |
|---|---|---|
| `Database:Provider` | `Sqlite` *(default)* | Local development — zero setup, `giftsofthegivers.db` auto-created |
| `Database:Provider` | `SqlServer` | Connecting to **Azure SQL** / SQL Server |

### Local development with Azure SQL

1. In `appsettings.json` (or better, `dotnet user-secrets`), replace the connection string:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=tcp:<your-server>.database.windows.net,1433;Initial Catalog=<your-db>;Persist Security Info=False;User ID=<your-admin>;Password=<your-password>;Encrypt=True;TrustServerCertificate=False;Connection Timeout=30;"
  },
  "Database": {
    "Provider": "SqlServer"
  }
}
```

2. Run the app — schema and seed data are created automatically (`EnsureCreated`).
3. Allow your machine in Azure SQL networking: Azure Portal → your SQL Server →
   **Networking** → *Add your client IPv4 address*.

> Tip: avoid committing your password. Use Visual Studio's *Connected Services →
> User Secrets*, or `dotnet user-secrets set "ConnectionStrings:DefaultConnection" "..."`.

### In Azure App Service (production)

Don't paste secrets into `appsettings.json` for deployment. Set **Application
Settings / Environment variables** on the App Service (Portal → App Service →
Environment variables):

| Name | Value |
|---|---|
| `ConnectionStrings__DefaultConnection` | your Azure SQL connection string |
| `Database__Provider` | `SqlServer` |
| `Functions__BaseUrl` | `https://<your-function-app>.azurewebsites.net` |

(Notice the `__` separator — it maps to `:` in configuration.)

The existing publish profile (`st10439690 - Web Deploy`) deploys the web app; add
these app settings first so the deployed site connects to your database and the
deployed function app.

## Section A — Azure Functions (30 marks)

### A.1 Function project in the solution ✔ (code done)

The `Function` project is in the solution with **two HTTP-triggered functions**:

1. **`TaxCertificate`** — called by the web app when a donor completes the donation
   form. Returns a dummy tax certificate (JSON via POST, HTML via GET).
2. **`LogProjectUpdate`** — called by the web app when an employee posts a project
   update. Writes the update to **Azure Blob Storage** (container
   `project-update-logs`) via an output binding.

The web app integrates with both in:
- `Controllers/DonationController.cs` → `FunctionClient.RequestTaxCertificateAsync(...)`
- `Controllers/EmployeeController.cs` → `FunctionClient.LogProjectUpdateAsync(...)`
- `Services/FunctionClient.cs` — the integration client (graceful fallback when the
  function app is offline).

📸 **Screenshot to take:** Visual Studio Solution Explorer showing all four projects
+ the two functions in the `Function` project.

### A.2 Run and test locally

1. Open the solution in Visual Studio. Set **both** projects to start:
   right-click the solution → *Configure Startup Projects* → set `Function` *and*
   `GiftOfTheGivers` to **Start** (or `Start without debugging`).
2. F5. The web app opens on `localhost:5116`, the function app listens on
   `localhost:7071`.
3. **Browser test** (GET): open
   `http://localhost:7071/api/taxcertificate?reference=GTG-TEST-123&amount=500&donor=Thabo`
   → an HTML certificate is rendered.
4. **Postman test** (POST): `POST http://localhost:7071/api/taxcertificate` with
   body → raw → JSON:
   ```json
   {
     "DonationId": 12,
     "Reference": "GTG-20260924-AB12CD",
     "DonorName": "Thabo Mokoena",
     "Amount": 750,
     "Currency": "ZAR",
     "DonationType": "OneTime",
     "CreatedAtUtc": "2026-09-24T10:00:00Z"
   }
   ```
   → JSON certificate with a certificate number.
5. **End-to-end test**: donate through the web app (Donate → Checkout → submit).
   The confirmation page shows a green note:
   *"Tax certificate generated by the TaxCertificate Azure Function"*.
6. Optional — `LogProjectUpdate` writes to storage. Locally either run
   [Azurite](https://learn.microsoft.com/azure/storage/common/storage-use-azurite)
   (`npm install -g azurite && azurite`) or post to it after deploying (A.3).

📸 **Screenshots to take:** function running in console, browser certificate,
Postman request + response, web-app confirmation with the "generated by function" note.

### A.3 Deploy the Function to Azure

1. Right-click the `Function` project → **Publish…** → **Azure** →
   **Azure Function App (Windows)**.
2. Create a new Function App (name e.g. `st10439690-gotg-functions`, runtime
   **.NET 9 Isolated**, region *South Africa North*, use your student subscription).
3. After publish, the browser opens the function app. In the Azure Portal → your
   Function App → **Environment variables** → add `AzureWebJobsStorage` with the
   connection string of a Storage Account (create one, e.g. `st10439690gotgstore`)
   — this makes `LogProjectUpdate` work in the cloud.
4. Live URLs:
   - `https://<your-function-app>.azurewebsites.net/api/taxcertificate?reference=GTG-DEMO-1&amount=250&donor=Demo`
   - `POST https://<your-function-app>.azurewebsites.net/api/logprojectupdate`

📸 **Screenshots to take:** publish success, function app in the portal with both
functions listed, live URL response in the browser.

> The web app's function URL is configured in `appsettings.json` (`Functions:BaseUrl`).
> When deployed, set `Functions:BaseUrl` to your deployed function app URL
> (App Service → Environment variables) so the web app calls the cloud function.

## Section D — Azure Artifacts (20 marks)

The helper library `GiftOfTheGivers.Helpers` is already NuGet-packable (metadata in
the csproj) and **used by the web app, the function app and the tests**.

1. Create/publish the package:
   ```bash
   dotnet pack GiftOfTheGivers.Helpers/GiftOfTheGivers.Helpers.csproj -c Release
   ```
2. Azure DevOps → **Artifacts** → *Create feed* (e.g. `gotg-feed`) → *Connect to
   feed* → dotnet → follow the "add nuget.config / credential provider" steps.
3. Publish:
   ```bash
   dotnet nuget push GiftOfTheGivers.Helpers/bin/Release/GiftOfTheGivers.Helpers.1.0.0.nupkg `
     --source https://pkgs.dev.azure.com/<org>/<project>/_packaging/gotg-feed/nuget/v3/index.json `
     --api-key az
   ```
4. **Consume it back**: in `GiftOfTheGivers.csproj`, replace the `ProjectReference`
   to Helpers with `<PackageReference Include="GiftOfTheGivers.Helpers" Version="1.0.0" />`,
   restore from the feed and build. (Swap back to the ProjectReference afterwards so
   the solution stays buildable for the whole team.)
5. Usage evidence — the web app calls the helpers in the donation process:
   - `Controllers/DonationController.cs` → `DonationReferenceGenerator.Create(...)`
     and `TaxCertificateNumberFormatter.Format(...)`
   - `Function/TaxCertificateFunction.cs` → `TaxCertificateNumberFormatter.Format(...)`
   - `GiftOfTheGivers.Tests/DonationHelperTests.cs` → 9 unit tests over the helpers

📸 **Screenshots to take:** the feed with the published package, the package
version page, and the web app building with the PackageReference.

### Versioning & retention conventions (top-band evidence)

- The package uses [SemVer](https://semver.org/): `MAJOR.MINOR.PATCH`
  (currently `1.0.0`). When you change helper code, bump the `Version` in
  `GiftOfTheGivers.Helpers.csproj` — e.g. a new helper method → `1.1.0`.
- Pre-release builds use a suffix: `1.1.0-beta.1` (via
  `dotnet pack --version-suffix beta.1`).
- Feed retention: Azure Artifacts feed → ⚙ Settings → **Retention policy** —
  e.g. "keep latest 5 versions per package, unpick versions older than 30 days
  not pinned". Screenshot the settings page for evidence.

### Pipeline secrets management (Section C top band)

1. Azure DevOps → Pipelines → **Library** → *+ Variable group* → name it
   `gotg-secrets`. Add variables:
   - `sql-connection-string` (🔒 secret) — your Azure SQL connection string
   - `functions-base-url` — your Function App URL
2. In `azure-pipelines.yml`, uncomment `variables: [- group: gotg-secrets]`.
3. Secret values are masked in logs automatically — screenshot a run where a
   secret is used but not displayed. The same values should be set on the App
   Service as environment variables for the deployed site (see "In Azure App
   Service (production)" above).
